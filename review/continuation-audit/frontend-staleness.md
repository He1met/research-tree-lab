# F09：静态站成功返回 200 时的陈旧状态审计

结论：**已有独立于网络失败的时间陈旧机制，浏览器实测通过。** 当页面持续取得相同的成功 HTTP 200 静态快照，且快照记录时点过去超过 **36 小时**，页面显示“最后记录 · 陈旧”并变为琥珀色。成功刷新同一快照不会把它恢复为新鲜。因此，不能把当前实现描述为“只有断网才标陈旧”。

同时，**36 小时以内不能据绿点判断生产者存活**。在模拟停止发布 2 小时和 35 小时时，页面仍显示绿色圆点与“记录快照截至”。它没有独立的任务运行心跳，也没有按当前每小时发布频率判断错过时点。固定 36 小时的默认界限未直接写在界面中。这是显示含义和告警延迟的具体限制；规范未指定停更多久必须变色，不能擅自把它判成“时间陈旧逻辑完全缺失”。

## 范围与方法

- [可复跑审计](frontend-staleness.mjs) 启动独立本地静态服务器和无头浏览器。服务器从既有公开文件制作内存副本，固定返回同一字节与 HTTP 200；没有调用远端行情、模型、原生任务或用户现有浏览器。
- 使用 Playwright 时钟同时推进 `Date`、单调时钟和计时器，模拟浏览器持续打开及睡眠后恢复。没有停止 Mac、Codex 或 ChatGPT App，也没有修改系统时间。
- 测试快照为 `b8633ae1ad392b613c312e0754b472a0eace2ef3fb9caa2c3e4075114411679a`，记录时点 `2026-09-22T18:35:49.524051Z`。这只是已存在公开快照的隔离时间实验，不是新策略记录或真实停机事件。
- Chromium `153.0.8010.12` 和 WebKit `26.6`；Apple M5、arm64、16 GiB、Darwin 27.0.0。每浏览器 7 个时间点，35 个数据请求均为 200；没有页面错误或“浏览器时钟异常”警告。
- `web/src`、`site/data`、`.local/store` 共 160 个文件审计前后哈希完全相同。四项 ACTIVE 业务任务及源码审批未操作。
- 运行：`node review/continuation-audit/frontend-staleness.mjs`。依赖使用已有项目本地 Playwright，不安装全局软件。

## 实测结果

| 快照年龄 | Chromium | WebKit | 页面提示 |
|---|---|---|---|
| 1 小时 | 尚未标陈旧 | 尚未标陈旧 | 绿色圆点；记录快照截至 |
| 2 小时，已跨多个小时发布槽位 | 尚未标陈旧 | 尚未标陈旧 | 同上；无生产者运行证明 |
| 35 小时 | 尚未标陈旧 | 尚未标陈旧 | 同上 |
| 36 小时前 2 秒 | 尚未标陈旧 | 尚未标陈旧 | 同上 |
| 恰好 36 小时 | 尚未标陈旧 | 尚未标陈旧 | 比较条件为严格大于 |
| 36 小时后 2 秒 | 陈旧 | 陈旧 | 最后记录 · 陈旧；琥珀色 |
| 48 小时 | 陈旧 | 陈旧 | 同上 |

在超过 36 小时之后，手动刷新仍成功读取 200 的 `latest.json`、manifest、catalog、history，快照身份不变且陈旧状态不清除。切入历史视图显示“历史时点”，不把它当当前新鲜数据；切回最新视图仍为陈旧。

## 源码与既有覆盖

- [App.tsx](../../web/src/App.tsx)：第 171–185 行，成功读取同一 snapshot 不替换原快照，清除的是读取错误；第 189 行每分钟刷新，第 190–194 行每秒更新当前时间；第 300–301 行按 `now - catalog.as_of > 36 * 3600_000` 或读取错误计算陈旧；第 308 行显示文本与颜色。
- [data.ts](../../web/src/data.ts)：加载结果附带 `receivedAt`，但 UI 陈旧判断使用快照 `as_of`，所以新的成功读取时间不会给旧记录续期。
- [observer.spec.ts](../../tests/browser/observer.spec.ts)：此前覆盖请求失败保留旧快照、执行条件到期及系统时钟跳变，缺少“成功 200、同一快照、正常时间推进跨 36 小时”的专门案例。本次审计补足该场景的独立回执，未改原测试套件或生产源码。

## 最小改进建议

1. **优先消除绿点的运行含义歧义。** 未达到陈旧界限时可保留准确记录时点，同时明确“发布者运行状态未知”，不以绿点暗示本机或任务健康。显示记录年龄及“超过 36 小时标陈旧”的规则即可解释现有行为；这不需要新心跳或修改研究数据。
2. 若要在每小时发布停止后更早提示，应另制定并公开“允许停更时长”政策，再从经核验的发布元数据读入。不能把浏览器成功 HTTP 200 当作生产者心跳，也不能根据未知的原生下一触发时间自行编造故障或重启理由。用户变频时必须保持实际设置优先。
3. 将本次成功 200 边界案例纳入未来正式回归即可；当前为只读审计，不提出立即修改已冻结源码。没有证据要求重启 App、修改已启用任务或启动远程自救。

F09 可据此确认“静态站仍可用但不再更新时，超过既定 36 小时会陈旧”的工程行为。它仍不是整机真实停机到恢复、自然原生续跑、认证处理或远程自救的实测证明。
